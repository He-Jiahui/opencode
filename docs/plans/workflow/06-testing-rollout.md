## 1. 事故还原用例(必须先红后绿)

这些用例直接取材于 2026-07-04 ZirconEngine 运行事故,是整个计划的"不再复发"证明:

### T-0 控制面卡死(对应 02)

1. 构造 1 requirements + 2 下游依赖的 workflow,推进 requirements 至 `planning`;
2. 以 department_pm 身份 dispatch `milestone_status done`
   → 断言:同步返回 `applied=false, code=illegal_transition`,
   `allowedTransitions` 含 `executing`;
3. 依提示 dispatch `plan_complete`(或 main_pm `force_complete`)
   → 断言:`applied=true`,outcome 携带新状态;下一 tick 两个下游进入 ready;
4. 全程 journal/commands.jsonl 有完整记录;任何路径不得出现 "queued" 字样的返回。

### T-1 干预不投递(对应 03)

1. requester 对 main_pm 发 direct 消息("忽视 planning 直接推进"),timing=interrupt;
2. 断言:main_pm session 被唤起且首条输入含 `<workflow-inbox>`;main_pm ack 后
   消息状态 `acked`;journal messages.jsonl 含 queued→delivered→acked 三条且
   时间差 < tick 周期 ×2;
3. 变体:main_pm 拒不 ack → deadline 后状态 `expired`,requester 收到升级通知。

### T-2 失败依赖饿死(对应 04)

1. 依赖里程碑转 `failed`;
2. 断言:两个 tick 内传递下游全部 `blocked(dependency_failed)`,main_pm 收到
   子图 report;
3. main_pm `force_skip` 失败依赖 → 下游 ready。

### T-3 folder reset 毁产物(对应 01)

1. agent 在 `work/staff/` 与 `work/milestones/x/` 写入产物;
2. 连续 3 次 `update_xml` 图重构(含删除里程碑 x);
3. 断言:`work/` 全区逐字节不变;x 状态 `cancelled` 且在 views 中标记移除;
   `graph/` 含 3 个修订文件。

### T-4 双目录分叉(对应 01/05)

1. 手工复制工程目录为两份(模拟事故的 帮你/帮我 分叉);
2. 断言:引擎 resume 拒绝启动并指向 doctor;`doctor --fix` 后仅存高水位目录,
   另一份被改名留档,workflow 可继续。

## 3. 端到端金丝雀

`company-flow.test.ts` 增加一条**全链路剧本**(mock provider 驱动,固定脚本):

> requester 提需求 → main_pm 规划 3 里程碑 → department_pm 细化并 plan_complete →
> 2 executor 并行执行(其一中途被 requester direct 干预改需求)→ reviewer 复审
> 打回一次(rejected→返工)→ tester 报告通过 → expert 被 consult 一次并回答 →
> main_pm + requester 验收 → completed。
>
> 全程断言:journal 无 expired/failed 消息、无非法转换、`work/` 无引擎写入、
> 结束后 doctor 全绿、从 workflow-state.json 删库重建后 graph 等价。

该剧本作为 CI 常驻回归,任何 workflow 改动必须通过。

## 4. 分阶段落地

| Phase | 内容 | 前置 | 退出条件 |
|-------|------|------|---------|
| 0 止血 | 02:命令同步化、转换表、update_xml 校验、幂等键 | — | T-0 绿;既有 company-flow 全绿 |
| 1 目录契约 | 01:新布局、manifest、WorkflowFs、原子写、废 reset;05 的 doctor 骨架(--migrate) | Phase 0 | T-3、T-4 绿;ZirconEngine 目录可迁移 |
| 2 协作协议 | 03:消息统一、投递循环、超时升级、status_update、standup | Phase 0(投递依赖 tick) | T-1 绿;咨询/干预旧表迁移完成 |
| 3 调度增强 | 04:失败策略、pipeline 组、reconciliation、staffing 细化 | Phase 0/2 | T-2 绿;金丝雀剧本绿 |
| 4 恢复自检 | 05:portable v2、幂等恢复、doctor 完整版 | Phase 1 | 05 验收全绿;金丝雀含删库重建断言 |

原则:

- Phase 0 独立成 PR、优先合入——它单独就能解除"公司停摆"这个最痛的点,
  且不依赖目录改版;
- 每 Phase 的 schema/DB 变更附迁移;portable state 版本号只在 Phase 1(布局)
  与 Phase 4(内容)各升一次;
- ZirconEngine 的真实工程目录作为迁移与恢复测试的长期 fixture
  (脱敏复制进 `test/workflow/fixtures/`)。
